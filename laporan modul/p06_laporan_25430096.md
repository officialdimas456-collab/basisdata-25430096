## 1. Tujuan Praktikum

Setelah menyelesaikan praktikum ini, mahasiswa diharapkan mampu:

1. Menambahkan data ke dalam tabel menggunakan perintah `INSERT`.
2. Mengubah dan menghapus data menggunakan perintah `UPDATE` dan `DELETE`.
3. Menggunakan mode aman untuk mencegah perubahan data yang tidak disengaja.
4. Melakukan pengujian positif dan negatif terhadap aturan integritas basis data.
5. Menyusun data sampel dan skenario pengujian untuk proyek basis data Sistem Informasi Akademik.

## 2. Ringkasan Dasar Teori

Data Manipulation Language (DML) merupakan bagian dari SQL yang digunakan untuk mengelola isi tabel dalam basis data.

Perintah DML yang digunakan dalam praktikum ini meliputi:

| Perintah | Fungsi |
|---|---|
| `INSERT` | Menambahkan data baru ke dalam tabel. |
| `UPDATE` | Mengubah data yang sudah tersimpan. |
| `DELETE` | Menghapus data dari tabel. |
| `SELECT` | Menampilkan dan memeriksa data. |

Dalam pengelolaan basis data akademik, pengisian data harus memperhatikan hubungan antara tabel induk (seperti `mahasiswa`, `dosen`, `mata_kuliah`) dan tabel anak (`pemilih_krs`, `detail_krs`, `nilai_khs`) melalui *Primary Key* dan *Foreign Key*.

Pengujian dilakukan melalui dua jenis pengujian, yaitu **uji positif** untuk memastikan data KRS/akademik yang valid dapat diterima, dan **uji negatif** untuk memastikan data yang melanggar *constraint* (seperti NIM ganda atau nilai di luar rentang valid) ditolak oleh server.

## 4. Jawaban Titik Analisis

### 4.1 Titik Analisis 1

**Mengapa `INSERT ... SELECT` lebih aman daripada mengetik angka secara manual? Apakah perubahan harga barang/SKS mata kuliah akan mengubah data transaksi sebelumnya?**

`INSERT ... SELECT` lebih aman karena nilai disalin secara otomatis dan dinamis dari tabel sumber, sehingga menghindari *human error* atau salah ketik. Perubahan harga/SKS di tabel master setelah transaksi terjadi tidak akan mengubah riwayat nilai pada detail transaksi terdahulu karena nilainya sudah dibekukan (*snapshot*) pada saat perintah disisipkan.

### 4.2 Titik Analisis 2

**Mengapa menghapus nota/KRS dapat menghapus detailnya, sedangkan menghapus petugas/dosen ditolak?**

Hal tersebut disebabkan oleh perbedaan konfigurasi *Foreign Key*. Klausa `ON DELETE CASCADE` pada detail transaksi membuat baris anak otomatis terhapus saat header transaksi dihapus. Sementara itu, penghapusan data dosen/petugas induk ditolak oleh server (`ERROR 1451`) karena data tersebut masih dirujuk oleh tabel pengisian KRS/transaksi. Solusi terbaik adalah mengubah status akun menjadi 'nonaktif', bukan menghapus barisnya.

### 4.3 Titik Analisis 3

**Mengapa aturan prasyarat atau kuota kelas tidak selalu dapat dijaga menggunakan CHECK?**

*Constraint* `CHECK` hanya dapat mengevaluasi nilai yang berada pada baris (*row*) yang sedang diisi atau diubah secara terisolasi. `CHECK` tidak dapat melakukan kueri ke tabel lain untuk menghitung kuota peserta kelas yang sudah terisi atau memeriksa status kelulusan mata kuliah prasyarat. Validasi lintas tabel tersebut membutuhkan fungsi pembantu, *trigger*, atau penanganan di tingkat aplikasi.

### 6.5 Utang Desain untuk Modul 14

Salah satu hasil pengujian (skenario `UJ-10`) menunjukkan bahwa mahasiswa berstatus 'nonaktif' masih dapat melakukan pengisian KRS. Hal ini terjadi karena aturan *Foreign Key* hanya memverifikasi keberadaan `id_mahasiswa` di tabel master, tanpa memeriksa kolom `status_mahasiswa`.

Temuan ini dicatat sebagai **utang desain (design debt)** yang akan diperbaiki pada Modul 14 menggunakan validasi lanjutan (*Trigger* / Stored Procedure).

## 7. Pembahasan dan Kendala

Selama praktikum DML, pengisian data harus dilakukan secara hierarkis (tabel master lebih dahulu, dilanjutkan tabel transaksi) agar tidak melanggar *Foreign Key constraint*.

Pada pengerjaan proyek Akademik `akad_096`, sempat ditemukan kendala ketika tipe data `id_krs` pada tabel `pemilih_krs` adalah `INT UNSIGNED AUTO_INCREMENT`, namun skrip masukan sempat menggunakan format string `KRS-2026-0001`. Hal tersebut menyebabkan galat tipe data pada MariaDB. Kendala ini diselesaikan dengan menyesuaikan masukan menjadi nilai integer acuan yang sesuai dengan tipe data pada DDL Modul 5.

Pengujian juga mengonfirmasi bahwa *Foreign Key* dan *Check Constraint* efektif mencegah data tidak valid, namun validasi aturan bisnis yang kompleks (seperti status aktif mahasiswa) membutuhkan mekanisme tambahan.
